# Admin-provisioned username/password accounts

Google login and first-time Google signup remain enabled. Public `register` and `getregistercode` endpoints return 403; the login page no longer links to self-registration. Existing email/password clients remain compatible: the legacy `Email` login field accepts either an email or a local username. Local usernames are case-insensitive and cannot contain `@`.

Only the Admin role can call `api/Account/admin/users` endpoints or see credential actions in the user list:

- GET `by-email?email=...`: find an existing account without exposing password hashes.
- POST: create a new active account with full name, username and password; email is optional. Assign only the existing User role.
- PUT `{userId}/credentials`: add a username and password to an existing passwordless account. Keep its UserId, email, profile, roles and all owned data. Never overwrite an existing password.
- POST `{userId}/reset-password`: explicitly replace an existing password, clear temporary password lockout, revoke every access/refresh session and invalidate outstanding emailed reset codes. This does not unlock an account disabled by an Admin.
- POST `{userId}/revoke-sessions`: revoke every device's access and refresh tokens. The account can still sign in again with its current credentials.
- POST `{userId}/lock`: disable the account indefinitely and revoke every session. Password and Google sign-in are denied until an Admin unlocks it. The current Admin cannot lock their own account.
- POST `{userId}/unlock`: enable the account again, clear temporary password lockout and failed attempts, and revoke old sessions again; the user must sign in with new tokens. For a leaked password, lock, reset the password, then unlock.

The user list has an Admin-only **Bảo mật tài khoản** menu with these three session actions and confirmation dialogs. Pending actions cannot be submitted twice; errors keep the dialog open for retry. Revoking the current Admin's sessions signs that Admin out. Status displays **Đã khóa** for disabled accounts. Successful actions write the existing audit trail in the same transaction as the account/token changes; an audit failure rolls back the change.

Migration `0039_ThemPhienBanPhienDangNhap.sql` adds `SessionVersion` to `AspNetUsers` and `RefreshToken`. JWTs carry a `session_version` claim. Every authenticated protected request checks the current account/version, so a revoked access token receives 401 on its next protected request even before expiry. Old JWTs without this claim use version 0 for rollout compatibility and become invalid on the first revocation. Unlocking does not restore old tokens. Public anonymous content remains public. A request already in progress is not cancelled by revocation.

Revocation increments the version, rotates Identity's concurrency stamp and revokes refresh rows atomically. Stale Identity updates cannot overwrite an Admin lock. Refresh rotation consumes the old refresh token once in a transaction; replay is rejected. `logoutalldevice` requires authentication and restricts the target to the current user or an Admin. Ordinary active-account checks do not revoke sessions. Concurrent frontend requests share one refresh attempt and all terminate on refresh failure instead of waiting indefinitely.

The create form checks email only when supplied. An omitted, empty or whitespace email is stored as NULL, allowing multiple email-less accounts. Identity's standard username validation remains enabled; OptionalEmailUserValidator validates and rejects duplicate supplied emails. For an existing passwordless account the form switches to an explicit confirmation step; an existing account with a password cannot be overwritten through Create. Username collisions are rejected. New passwords use Identity hashing/validation (minimum 8 characters, upper/lowercase, digit and special character). Credential writes, role assignment and audit commit in one database transaction. Passwords/confirmation values are not returned or recorded in audit/logs; existing historical logs are not deleted by this change. Email-less users sign in with username and contact the admin for password resets; Google login is unchanged.

No new user table is required. Migration `0037_DamBaoEmailTaiKhoanKhongTrung.sql` makes the existing NormalizedEmail index unique to protect concurrent Google/admin account creation. It deliberately fails instead of merging/deleting users if historical normalized emails are duplicated. Deploy API and Client together; normal API startup applies the script.

Targeted verification covers Admin-only access, disabled public registration, duplicate email/username, password overwrite protection, safe account lookup, username/email login resolution, password-free audit/log output and the unique email model. Account security tests use local HTTP, real Identity/repositories and an isolated SQLite database to cover revoke/lock/unlock, old access/refresh rejection, reset without unlocking, audit rollback, refresh replay and stale Identity updates. The frontend tests cover confirmation, errors, self-lock protection and concurrent refresh completion. PostgreSQL migrations, external Google sign-in and deployed browser interaction still need deployment smoke testing; tests do not change real users.

Local verification on 2026-10-08: 33 selected backend tests and all 61 frontend tests passed; API and Client production builds passed. Angular template tests render the real user list dropdown and confirmation modal, check disabled self-lock, unlock selection, loading/error states and escaped account names. Browser verification reached the local login page, but the Google popup did not complete sign-in, so Admin layout checks at 1440/1024/768/390 and live account operations remain deployment smoke tests. No PostgreSQL migration or real account lock/unlock/revocation was performed during this verification.
